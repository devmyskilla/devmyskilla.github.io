# تصميم التحكم الشامل بالموقع من Decap CMS

التاريخ: 2026-08-31

## 1. الهدف

تحويل **دنيا الدورات** إلى موقع تكون فيه لوحة **Decap CMS** نقطة التحكم في كل المحتوى والهوية القابلة للتحرير، بحيث لا يحتاج مدير الموقع إلى تعديل HTML أو JavaScript أو GitHub يدويًا عند تغيير نص أو رابط أو صورة أو ترجمة أو إعداد SEO أو بيانات منصة.

الهدف لا يشمل جعل Decap محررًا لبنية الصفحة أو منطق JavaScript. **الهيكل البرمجي، المكونات، وسلوك التطبيق تبقى في الكود**؛ أما كل قيمة مرئية أو تحريرية أو مرتبطة بالمحتوى فتأتي من البيانات.

## 2. معيار النجاح

يُعد التغيير ناجحًا عندما يستطيع مدير الموقع من `/admin/` تعديل ونشر ما يلي دون لمس الكود:

- اسم الموقع واسم الجهة المطورة وحقوق النشر.
- جميع النصوص العربية والإنجليزية والتركية في كل الصفحات.
- نصوص الأزرار والقوائم والفلاتر والرسائل والحالات الفارغة ورسائل الخطأ.
- نصوص الصفحة الرئيسية وصفحة الاستكشاف وصفحة تفاصيل المنصة والاختبار والمقارنة.
- أسماء التصنيفات واللغات وترجماتها.
- جميع روابط الموقع القابلة للتحرير.
- الشعار والأيقونات والصور ونصوص `alt` المرتبطة بها.
- بيانات SEO القابلة للتحرير لكل صفحة ولكل لغة.
- بيانات المنصات ومعلوماتها التحريرية والتقنية الحالية.
- ترتيب المنصات وتمييزها.

ويجب أن تبقى المنصات الحالية وعددها 110 محفوظة أثناء الهجرة.

## 3. الحدود المتعمدة

### داخل CMS

كل محتوى أو قيمة تظهر للمستخدم أو تصف الصفحة أو تشير إلى مورد خارجي تكون قابلة للتحرير، بما في ذلك النصوص، الصور، الأيقونات المرئية، الروابط، نصوص الوصول، بيانات SEO، التصنيفات، اللغات، وبيانات المنصات.

### خارج CMS

تبقى في الكود:

- بنية HTML والمكونات.
- منطق البحث والتصفية والمقارنة والترشيح.
- منطق التخزين المحلي وService Worker.
- معرفات DOM والـCSS classes.
- مفاتيح البيانات التقنية الثابتة التي يعتمد عليها الكود.
- قواعد التحقق من صحة البيانات.

لا يوفّر هذا التصميم محرر HTML حرًا أو محرر JavaScript أو CSS عام من لوحة الإدارة. يمكن وضع **theme tokens محدودة** مثل لون الواجهة الأساسي أو لون المتصفح ضمن الإعدادات إذا كانت موجودة كقيم آمنة ومتحقق منها، لكن لا يسمح بحقن CSS خام.

## 4. البنية الجديدة لـ `data.json`

يبقى `data.json` المصدر الرئيسي الوحيد لمحتوى الموقع وقت التشغيل، ويُعاد تنظيمه إلى أقسام واضحة:

```json
{
  "settings": {},
  "assets": {},
  "seo": {},
  "siteText": {},
  "categories": [],
  "languages": [],
  "quiz": {},
  "comparison": {},
  "platforms": []
}
```

### 4.1 `settings`

يحتوي على إعدادات عامة غير مرتبطة بصفحة بعينها، مثل:

- `siteName` كقيمة مترجمة.
- `developerName` كقيمة مترجمة.
- `copyright` كقيمة مترجمة.
- `defaultLanguage`.
- روابط عامة، مثل رابط الجهة المطورة إذا أضيف.
- theme tokens آمنة عند الحاجة، مثل `themeColor`.

القيم التي تظهر بلغات متعددة تستخدم شكلًا موحدًا:

```json
{
  "ar": "دنيا الدورات",
  "en": "Dunya Al-Dawrat",
  "tr": "Dünya Kursları"
}
```

### 4.2 `assets`

يحتوي على جميع الأصول المرئية القابلة للتعديل، مثل:

- `brandLogo`.
- `favicon`.
- `heroImage` أو `heroLogo`.
- أي صور زخرفية مستخدمة في الواجهة.
- الأيقونات التحريرية/المرئية التي يريد مدير الموقع التحكم بها.

كل أصل يمكن أن يحتوي على:

```json
{
  "src": "/assets/uploads/example.webp",
  "alt": {
    "ar": "...",
    "en": "...",
    "tr": "..."
  }
}
```

الأيقونات النصية البسيطة مثل الرموز أو Unicode تحفظ كقيم نصية في البيانات إذا كانت جزءًا من المحتوى. الأيقونات التي تعتمد عليها وظيفة تقنية بحتة لا تتحول إلى محتوى قابل للتحرير إلا إذا كانت مرئية للمستخدم ويمكن استبدالها بأمان.

### 4.3 `seo`

يوجد قسم لكل صفحة رئيسية:

```text
seo.home
seo.explore
seo.platform
```

وكل صفحة تحتوي، لكل لغة، على:

- `title`
- `description`
- `ogTitle`
- `ogDescription`
- `ogImage`

عند تحميل الصفحة يقوم runtime SEO helper بتحديث `document.title` ووسوم `meta` وOpen Graph من `data.json` حسب اللغة المختارة.

**قيد معروف:** الموقع مستضاف كصفحات static على GitHub Pages، لذلك بعض روبوتات معاينة الشبكات الاجتماعية التي لا تنفذ JavaScript قد ترى القيم الأساسية الموجودة في HTML قبل التحديث الديناميكي. التصميم يضمن تحكم المستخدم في SEO داخل التطبيق؛ وإذا احتجنا لاحقًا إلى SEO مولد بالكامل قبل التحميل يمكن إضافة خطوة build منفصلة دون تغيير نموذج البيانات.

### 4.4 `siteText`

يحتفظ بجميع نصوص الواجهة العامة، لكنه ينظم بحسب مجموعات وظيفية بدل قائمة مفاتيح غير مرتبة.

المجموعات المنطقية المقترحة:

```text
common
navigation
home
explore
platform
filters
comparison
quiz
errors
footer
accessibility
```

ويكون كل عنصر مترجمًا إلى `ar/en/tr`. يمكن تمثيل الترجمة بإحدى طريقتين، لكن التطبيق يعتمد **طريقة واحدة فقط** في النسخة النهائية. التوصية هي جعل المفتاح هو المفهوم ثم وضع اللغات بداخله، مثل:

```json
"navHome": {
  "ar": "الرئيسية",
  "en": "Home",
  "tr": "Ana Sayfa"
}
```

هذا يجعل الحقل الواحد في CMS يعرض اللغات الثلاث معًا، وهو أسهل للمحرر من وجود ثلاث قوائم منفصلة ضخمة.

### 4.5 `categories`

يتم حذف خريطة التصنيفات الثابتة من `i18n.js` ونقلها إلى البيانات:

```json
{
  "id": "technology",
  "label": {
    "ar": "تكنولوجيا",
    "en": "Technology",
    "tr": "Teknoloji"
  },
  "icon": "...",
  "enabled": true,
  "displayOrder": 10
}
```

`id` هو المفتاح التقني المستقر الذي تستخدمه المنصات والفلاتر. يمكن تعديل الاسم والأيقونة والترتيب من CMS، أما تغيير `id` لمنشور قائم فيحمل تحذيرًا واضحًا لأنه قد يؤثر على البيانات المرتبطة.

### 4.6 `languages`

بنفس نمط التصنيفات:

```json
{
  "id": "English",
  "label": {
    "ar": "الإنجليزية",
    "en": "English",
    "tr": "İngilizce"
  },
  "enabled": true,
  "displayOrder": 10
}
```

يتم حذف `langMap` الثابتة من JavaScript، وتُبنى خيارات اللغة والترجمة من هذه القائمة.

### 4.7 `quiz`

يحتوي على النصوص والخيارات التحريرية الخاصة بالاختبار، بما في ذلك:

- العنوان والوصف.
- نصوص الأسئلة.
- أسماء الخيارات.
- النصوص النهائية ورسائل النتائج.

القيم التقنية المستخدمة في منطق الترشيح تبقى stable IDs منفصلة عن labels. تعديل labels لا يغير منطق الاختبار.

### 4.8 `comparison`

يحتوي على labels والرسائل الخاصة بواجهة المقارنة، بينما تبقى خوارزمية اختيار الصفوف ومنطق المقارنة في JavaScript.

### 4.9 `platforms`

تبقى قائمة المنصات الحالية مع توسيع الترجمة والإدارة المنظمة. المنصة تشمل، حسب المتاح:

- `id` تقني مستقر.
- الاسم والترجمات إن وجدت.
- الوصف `ar/en/tr`.
- `categoryId` بدل الاعتماد على نص التصنيف.
- `languageIds` بدل الاعتماد على أسماء عرض قابلة للتغيير.
- نموذج السعر.
- حالة المحتوى المجاني.
- توفر الشهادات والشهادات المجانية.
- الروابط الرسمية والكتالوج.
- الشعار والصور ونصوص alt.
- عدد المحتوى الرسمي ونوعه.
- تاريخ آخر تحقق.
- مناسب لـ، نقاط القوة، القيود لكل لغة.
- featured/displayOrder.

الهجرة تحفظ جميع البيانات الحالية ولا تخمّن حقائق جديدة.

## 5. طبقة runtime

### 5.1 DataLoader

يظل `js/data-loader.js` مسؤولًا عن جلب `data.json` والتحقق من البنية الأساسية. يتم توسيع التحقق ليشمل الأقسام الجديدة وأنواعها.

التحقق يميز بين:

- **حقول مطلوبة لكامل تشغيل الموقع**: يجب وجودها أو إظهار fallback آمن.
- **حقول اختيارية**: غيابها يؤدي إلى إخفاء العنصر لا إلى ظهور نص `Unknown` غير مرغوب.

### 5.2 Content API صغيرة وواضحة

بدل وصول الصفحات مباشرة إلى كائن JSON في أماكن كثيرة، يضاف/يعاد تنظيم helper صغير يقدم وظائف محددة مثل:

```text
getText(key, lang)
getSetting(key, lang)
getAsset(key, lang)
getCategoryLabel(id, lang)
getLanguageLabel(id, lang)
getSeo(page, lang)
```

هذا يعزل شكل البيانات عن مكونات الصفحة ويسهل الاختبار والهجرة المستقبلية.

### 5.3 i18n

`js/i18n.js` يتوقف عن احتواء قاموس محتوى كبير أو خرائط تصنيفات ولغات ثابتة.

يبقى فيه فقط:

- إدارة اللغة الحالية.
- اتجاه الصفحة RTL/LTR.
- تطبيق القيم المترجمة على DOM.
- fallback تقني محدود جدًا في حالات فشل البيانات، وليس محتوى الموقع الطبيعي.

لا تبقى النصوص الأساسية للموقع hardcoded داخله.

### 5.4 HTML

تتحول النصوص المرئية المتبقية في HTML إلى نقاط ربط بيانات (`data-*` أو عناصر ذات IDs/keys واضحة)، مثل:

- اسم الجهة المطورة.
- نصوص الوصول المرئية.
- العناوين التي ما زالت literal.
- أي labels ثابتة.
- الصور والأصول القابلة للتحرير.

لا يتم حقن HTML غير موثوق من CMS. النصوص تدخل كـ`textContent` والقيم الأخرى عبر خصائص آمنة بعد التحقق.

## 6. Decap CMS

### 6.1 تنظيم لوحة الإدارة

تقسم لوحة Decap إلى أقسام مفهومة بدل ملف واحد ضخم:

1. إعدادات الموقع
2. الهوية والصور
3. الصفحة الرئيسية
4. صفحة المنصات
5. صفحة التفاصيل
6. الاختبار والترشيحات
7. المقارنة
8. التصنيفات
9. اللغات
10. SEO
11. المنصات

يمكن أن تبقى هذه الأقسام كلها مرتبطة فعليًا بـ`data.json` عبر file collections/object fields، لكن واجهة `config.yml` يجب أن تعرضها بطريقة منطقية للمحرر.

إذا فرض Decap قيودًا تجعل فصل نفس الملف إلى عدة entries غير عملي، فالبديل المقبول هو إبقاء entry واحد مع object groups مطوية ومنظمة بعناوين واضحة. **لا يتم تقسيم مصدر runtime إلى عدة ملفات فقط من أجل شكل لوحة الإدارة** إلا إذا أثبت التنفيذ أن Decap يتطلب ذلك.

### 6.2 الصور والوسائط

يستمر استخدام:

```text
media_folder: assets/uploads
public_folder: /assets/uploads
```

حقول الصور تستخدم widget `image` بدل string عندما يكون المورد صورة فعلية، بما يسمح بالرفع والاختيار من Media Library.

### 6.3 المعرفات التقنية

المعرفات مثل `platform.id`, `category.id`, و`language.id` تظهر بتسمية واضحة:

> معرّف تقني — لا تغيّره بعد النشر إلا إذا كنت تعرف أثر ذلك.

حيثما يسمح Decap، تكون غير مطوية أو محمية بصريًا/مفسرة بدل أن تبدو كحقل نص عادي بلا تحذير.

### 6.4 مولد config

يبقى `scripts/generate-decap-config.cjs` هو المصدر المولد لـ`admin/config.yml` حتى لا يعود عدم التطابق الذي ظهر سابقًا.

يجب أن يولد:

- إعداد GitHub backend الحالي.
- `base_url` الخاص بـCloudflare Worker.
- الحقول الجديدة كلها.
- حقول الصور والروابط والترجمة بالشكل الصحيح.

واختبار `--check` يبقى جزءًا من CI.

## 7. الروابط والأصول

كل رابط يمكن أن يغيره مدير المحتوى يجب أن يأتي من البيانات، بما في ذلك روابط CTA، الجهة المطورة، وروابط المنصات.

الروابط الداخلية التقنية التي يحددها الراوتر/تنقل التطبيق مثل `platform.html?id=...` يمكن أن تبقى مولدة في JavaScript لأنها ليست محتوى تحريريًا؛ لكن **نص الرابط** وأي وجهة خارجية قابلة للتحرير تكون من CMS.

كل أصل مرئي متحكم به من CMS يجب أن يمر عبر helper يتحقق من قيمة المسار/URL قبل وضعها في DOM.

## 8. SEO واللغة

عند تغيير اللغة:

- تتغير النصوص المرئية.
- يتغير `document.title`.
- تتغير `meta[name="description"]`.
- تتغير Open Graph tags المدارة من البيانات.
- تتغير نصوص `alt` للصور.
- يبقى `html.lang` و`html.dir` متزامنين.

لا يتم تغيير معرفات البيانات أو URLs التقنية عند ترجمة labels.

## 9. fallback والأخطاء

المبدأ: **غياب المحتوى الاختياري يعني إخفاءه، لا اختراع قيمة.**

إذا فشل `data.json` كليًا، يعرض الموقع رسالة فشل تقنية مختصرة وآمنة بدل صفحة بيضاء. هذه الرسالة التقنية الوحيدة يمكن أن تبقى fallback داخل bundle لضمان أن فشل مصدر المحتوى لا يمنع إظهار الخطأ نفسه.

إذا كان قسم اختياري ناقصًا:

- لا تظهر كلمة "Unknown" إلا إذا كان التصميم يطلبها صراحة.
- الأصول الاختيارية تختفي أو تستخدم fallback تقنيًا موثقًا.
- الروابط غير الصالحة لا تُعرض كروابط قابلة للنقر.

## 10. استراتيجية الهجرة

الهجرة تتم دون خسارة بيانات وبترتيب يقلل المخاطر:

1. إضافة tests تصف المخطط الجديد قبل تغييره.
2. توسيع `data.json` وإعادة ترتيب المحتوى الحالي آليًا/حتميًا قدر الإمكان.
3. نقل التصنيفات واللغات الحالية من خرائط JavaScript إلى JSON مع الحفاظ على IDs المتوافقة.
4. نقل النصوص المرئية الثابتة من HTML/JS إلى البيانات.
5. إضافة Content API/runtime helpers.
6. تحديث الصفحات لاستخدام المصدر الجديد.
7. تحديث مولد Decap ثم توليد `admin/config.yml`.
8. تحديث Service Worker/cache version لأن schema وadmin config تغيرا.
9. تشغيل الاختبارات والتحقق من 110 منصة.
10. نشر النسخة الجديدة والتحقق من `/admin/` وتسجيل الدخول والتحرير.

لا يتم حذف مصدر قديم قبل أن تصبح الاختبارات المقابلة للمصدر الجديد ناجحة.

## 11. الاختبارات المطلوبة

### اختبارات البيانات

- `data.json` صالح JSON ويحتوي الأقسام المطلوبة.
- عدد المنصات = 110 بعد الهجرة.
- كل `categoryId` يشير إلى تصنيف موجود.
- كل `languageId` يشير إلى لغة موجودة.
- stable IDs فريدة.
- الحقول المترجمة الرئيسية تحتوي بنية صحيحة.

### اختبارات عدم وجود محتوى ثابت

إضافة اختبارات تستهدف **المواضع المعروفة** للنصوص المرئية داخل HTML/JS وتمنع رجوع محتوى كان يجب أن يأتي من CMS.

لا نستخدم اختبارًا ساذجًا يمنع كل string literal في JavaScript، لأن الكود يحتاج قيمًا تقنية. الاختبارات تركز على user-facing copy والأصول والخرائط التي تم نقلها.

### اختبارات runtime

- `getText` يعيد اللغة الصحيحة ويطبق fallback المتفق عليه.
- التصنيفات واللغات تُترجم من البيانات لا من hardcoded maps.
- تغيير اسم الموقع ينعكس على الصفحات المعنية.
- تغيير أصل/شعار ينعكس على DOM.
- تغيير SEO يحدّث title/meta.
- تغيير اللغة يحدث النصوص وalt وSEO والاتجاه.

### اختبارات Decap

- `admin/config.yml` مولد من السكربت الحالي.
- OAuth proxy محفوظ.
- حقول الصور تستخدم Media Library.
- كل المجموعات الأساسية قابلة للتحرير.
- لا يوجد Client Secret في المستودع.

### اختبارات CI والنشر

يجب أن تنجح:

```text
node --test tests/*.test.cjs
JavaScript syntax checks
JSON validation
generate-decap-config.cjs --check
legacy runtime dependency checks
git diff --check
```

بعد الدمج يجب أن ينجح GitHub Pages deployment أيضًا.

## 12. التوافق مع النظام الحالي

- يبقى GitHub Pages هو الاستضافة.
- يبقى Decap CMS هو لوحة الإدارة.
- يبقى GitHub backend مع Cloudflare OAuth proxy الحالي.
- لا تعود Supabase أو backend إضافي.
- لا يتم إدخال خدمة مدفوعة.
- `data.json` يبقى المصدر المركزي بدل إنشاء قاعدة بيانات جديدة.

## 13. قرارات معمارية نهائية

1. **المصدر المركزي:** `data.json` يبقى مصدر المحتوى الرئيسي.
2. **الترجمة:** كل مفهوم تحريري يحمل `ar/en/tr` معًا قدر الإمكان.
3. **التصنيفات واللغات:** تتحول من hardcoded maps إلى collections في JSON.
4. **الأصول:** الصور والشعارات وalt والأيقونات التحريرية تصبح CMS-managed.
5. **SEO:** CMS-managed ويطبق في runtime مع توثيق قيد static social crawlers.
6. **السلامة:** لا يسمح بحقن HTML/CSS/JS خام من CMS.
7. **المعرفات:** IDs التقنية مستقرة ومنفصلة عن labels القابلة للتحرير.
8. **Decap config:** يبقى مولدًا آليًا ويُفحص في CI.
9. **البيانات الحالية:** لا تُحذف ولا تُستبدل بمعلومات مخمنة أثناء الهجرة.
10. **الهيكل:** CMS يتحكم بالمحتوى والهوية والقيم القابلة للتحرير، وليس منطق التطبيق أو تخطيطه البرمجي.

## 14. تعريف الانتهاء

يُعتبر المشروع مكتملًا عندما يمكن، من لوحة `/admin/` فقط، إجراء اختبار عملي يتضمن:

- تغيير اسم الموقع في اللغات الثلاث.
- تغيير عنوان الصفحة الرئيسية وزر CTA.
- تغيير اسم تصنيف وترجماته.
- تغيير اسم لغة وترجماتها.
- رفع شعار/صورة جديدة وتغيير alt.
- تغيير عنوان SEO ووصفه.
- تعديل منصة موجودة.
- نشر التغييرات إلى GitHub.

ثم تظهر التغييرات في الموقع بعد نشر GitHub Pages، مع نجاح CI الكامل وبقاء الـ110 منصة سليمة.
